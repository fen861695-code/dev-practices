# 第 9 步：请人把关——代码评审入门

> 本步目标：理解代码评审的意义与流程，学会在 GitHub 上发起 Pull Request，知道评审看什么、如何回应意见。

## 1. 进度（导师话术）

"这一步我们请'第二双眼睛'帮我们看代码。哪怕是个人项目，走一遍评审流程也能发现盲点、养成专业习惯。"

## 2. 为什么

- 自己写的代码自己很难发现所有问题，旁观者往往一眼看出隐患。
- 评审是团队里知识共享、统一风格、互相学习的最重要方式。
- 所有进入主线的代码都经过评审，是工程质量的一道关键闸门。

## 3. 概念扫盲（作文请老师批改类比）

- **代码评审（Code Review）**：作者之外的人阅读代码，提出问题和建议，作者修改后再合并。
- **Pull Request（PR，拉取请求）**：在 GitHub 上正式提出"请把我这个分支的改动合并到主线"，并附上说明，评审就围绕它进行。
- **LGTM**："Looks Good To Me（我看可以）"，评审人批准的常用语。

## 4. 跟着做

### （1）在新分支上开发并推送

评审以"分支 + PR"进行。即使一个人，也走完整流程：

```
git checkout -b feature/add-tests
git add .
git commit -m "test: 添加工具函数单元测试"
git push -u origin feature/add-tests
```

解释：`git checkout -b 分支名` 创建并切换到新分支（在"平行草稿"上改，不影响主线 main），然后推送这个分支。

### （2）在 GitHub 上发起 PR

1. 打开 GitHub 仓库，会看到刚推送的分支提示 "Compare & pull request"，点击。
2. 填写 PR 说明，建议包含四块：
   - 这个 PR 做了什么
   - 为什么要做
   - 怎么测试的（如"运行 npm test，4 项全部通过"）
   - 有没有需要特别注意或破坏性的改动
3. 点 "Create pull request"。

### （3）评审看什么（对照清单）

让导师（AI）或同伴按以下角度逐条过一遍：

- 功能：是否正确实现、是否覆盖需求。
- 异常与边界：空值、找不到数据、网络失败等情况处理了吗。
- 可读性：命名是否达意、结构是否清晰、新人能否看懂。
- 安全：输入是否校验、有没有把用户输入拼进 SQL、有无敏感信息。
- 重复与冗余：有没有大段重复代码、调试残留、没用上的依赖。
- 测试：关键逻辑是否有测试、测试是否通过。

### （4）处理意见并合并

- 对每条意见逐一回应：采纳就修改，不采纳就礼貌说明理由，不要沉默忽略。
- 修改后在同一分支继续 commit、push，PR 会自动更新。
- 所有意见解决、检查通过后，点 "Merge pull request" 合并到主线，然后可删除该分支。
- 个人项目没有第二人时，让 AI 导师严格按清单"挑刺"，把发现的问题改完再合并，同样达到效果。

## 5. 检查一下

让小白截图：PR 页面（含说明、评审意见、合并状态）。确认他完成了"建分支 → 推送 → 发 PR → 评审 → 合并"完整闭环。

## 6. 学到了什么

1. 代码评审靠"第二双眼睛"发现盲点、共享知识，是专业团队的必经环节。
2. PR 是请求合并分支改动的正式入口，说明要写清"做了什么、为什么、怎么测"。
3. 评审意见要逐条回应；评审对事不对人，是学习而非批评。

## 7. 记到项目文档

在 `PROJECT_JOURNAL.md` 记录：PR 流程怎么走、评审发现了哪些问题、自己如何修改、对评审文化的理解。合并后切回 main 并 `git pull` 同步。

## 小白常见问题

- **Q：一个人做项目也要这么麻烦吗？** A：建议至少走一遍理解流程；真实协作中这是每天都在用的核心技能，越早熟悉越好。
- **Q：被指出很多问题是不是说明我很差？** A：完全不是，再资深的工程师也会被提一堆意见，评审就是为了让代码更好，和个人能力无关。
