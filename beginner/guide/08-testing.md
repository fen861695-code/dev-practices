# 第 8 步：检查自己的代码——测试入门

> 本步目标：理解测试的意义和类型，写出并运行第一个单元测试，建立"改完代码就跑测试"的习惯。

## 1. 进度（导师话术）

"这一步我们给代码配一个'自动检查员'。以后每次改动，它都能帮我们快速确认功能没被改坏，而不用每次都手动点一遍。"

## 2. 为什么

- 手动点页面验证又慢又容易漏，项目越大越靠不住。
- 测试可以反复、自动运行；改代码后一旦测试失败，立刻知道哪里坏了。
- 有测试垫底，重构和添加新功能时心里才有底。

## 3. 概念扫盲（写完作业对答案类比）

- **测试**：一段专门检查"另一段代码是否正确"的代码，自动给出"通过/失败"。
- **断言（assert）**：一句"我断定结果应该等于……"，与实际不符测试就失败。
- **单元测试**：盯着一个小函数，验证它在各种输入下输出正确（最常用、最快）。
- **集成测试**：检查几个部分协作是否正常（如后端和数据库）。
- **端到端测试（E2E）**：模拟真实用户在页面上点击，走完整流程。
- 测试金字塔：大量单元测试打底，少量集成测试，极少数 E2E 覆盖关键路径。

## 4. 跟着做

### （1）把可测的逻辑抽成纯函数

"纯函数"指同样输入永远得到同样输出、不依赖外部状态的函数，最容易测。
在项目里新建 `utils.js`，把"校验待办内容"的逻辑抽出来：

```javascript
function isValidTodoText(text) {
  return typeof text === 'string' && text.trim().length > 0;
}

module.exports = { isValidTodoText };
```

在 server.js 里引入并使用它（替换原来的内联判断）：

```javascript
const { isValidTodoText } = require('./utils');
// POST 接口里：
if (!isValidTodoText(req.body.text)) {
  return res.status(400).json({ error: '内容不能为空' });
}
```

讲解：把逻辑抽成独立、纯粹的函数，既好复用又好测试，这是专业开发的常用手法。

### （2）写第一个单元测试

新建 `utils.test.js`（Node.js 自带测试功能，无需额外安装）：

```javascript
const test = require('node:test');
const assert = require('node:assert');
const { isValidTodoText } = require('./utils');

test('正常内容应当有效', () => {
  assert.equal(isValidTodoText('买牛奶'), true);
});

test('空字符串应当无效', () => {
  assert.equal(isValidTodoText(''), false);
});

test('只有空格的内容应当无效', () => {
  assert.equal(isValidTodoText('   '), false);
});

test('非字符串内容应当无效', () => {
  assert.equal(isValidTodoText(undefined), false);
});
```

讲解测试三段式：**给定输入 → 调用函数 → 断言结果**。这里故意覆盖正常、空、纯空格、错误类型四种情况，包含"边界条件"。

### （3）运行测试

```
node --test
```

解释：Node 会自动找到 `.test.js` 文件并运行，输出通过（pass）/失败（fail）数量。全绿（通过）即代码符合预期。

### （4）让测试随项目常驻

- 在 package.json 的 scripts 里加一条：`"test": "node --test"`，以后直接 `npm test`。
- 养成习惯：每次写完或修改功能，先跑测试再提交；以后这些测试还会在 CI（第 12 步正式版规范里）自动运行。

## 5. 检查一下

让小白运行 `npm test` 并截图，应显示 4 个测试全部 pass。再故意让他把某个预期改错（如把 true 写成 false）观察测试变红，体会"测试在帮我们抓错"，然后改回。

## 6. 学到了什么

1. 测试是自动、可重复的代码检查；单元测试针对单个纯函数，遵循"输入—执行—断言"。
2. 要主动覆盖正常情况和边界（空值、错误类型），边界往往是 bug 藏身处。
3. 把逻辑抽成纯函数更好测；改完代码先跑测试是基本纪律。

## 小白常见问题

- **Q：测试代码会不会很多余、很花时间？** A：前期看似多花几分钟，但每次改动都能秒级验证，项目越复杂省下的时间越多，是性价比极高的投资。
- **Q：要测试哪些东西？** A：优先测试"业务逻辑和容易出错的地方"；界面展示类代码可用少量 E2E 覆盖，不必追求每行都测。
