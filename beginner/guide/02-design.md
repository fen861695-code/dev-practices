# 第 2 步：动手前先设计——页面与数据

> 本步目标：画出页面草图、想清楚要存哪些数据、数据怎么在前后端之间流动，并列出需要的"接口清单"。

## 1. 进度（导师话术）

"需求定了，这一步我们当'建筑师'，先在纸上把房子的图纸画出来：页面长什么样、要存哪些信息、信息怎么流转。"

## 2. 为什么

- 写代码前把结构想清楚，写的时候才不会走一步看一步。
- 提前想清楚"存什么数据、需要哪些接口"，前后端才能各自开工、最后顺利对接。

## 3. 概念扫盲

- **页面草图（线框图）**：用简单方框表示页面上有什么、摆在哪，不需要美术功底。
- **数据字段**：一条信息由哪些部分组成。比如一条"待办"有：编号、内容、是否完成、创建时间。
- **数据流动**：用户操作后，数据经过哪些环节。比如：点"添加" → 前端收集内容 → 发给后端 → 后端存进数据库 → 返回结果 → 前端刷新列表。
- **CRUD**：对数据的四种基本操作——增（Create）、查（Read）、改（Update）、删（Delete），几乎所有软件都是在做这四件事。

## 4. 跟着做

### （1）画页面草图

用纸笔或任意画图工具，画出待办清单页面，标注三块内容：
- 顶部：一个输入框 + "添加"按钮。
- 中间：待办事项列表，每条前面有个勾选框、后面有文字和"删除"按钮。
- 已完成的事项：文字加删除线（或变灰）。

### （2）设计数据

想清楚"一条待办要存哪些字段"，写成表格：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| id | 每条待办的唯一编号，用来区分两条内容相同的待办 | 1 |
| text | 待办的具体内容 | "买牛奶" |
| done | 是否已完成（是/否） | false |
| created_at | 创建时间 | 2026-10-12 10:00 |

### （3）梳理数据流动（以"添加待办"为例）

1. 用户在输入框打字，点"添加"。
2. 前端拿到文字，打包成一个"请求"发给后端。
3. 后端收到后，给它分配 id、补上时间，存进数据库。
4. 后端返回"成功"和新待办。
5. 前端把新待办加到页面列表里，输入框清空。

### （4）列接口清单（就是前后端之间的"菜单"）

| 要做的事 | 请求方式 | 地址（接口） |
| --- | --- | --- |
| 获取所有待办 | GET | /api/todos |
| 添加一条待办 | POST | /api/todos |
| 标记完成/取消 | PATCH | /api/todos/:id |
| 删除一条待办 | DELETE | /api/todos/:id |

向小白解释：GET 像"查看菜单"，POST 像"下单"，PATCH 像"改订单"，DELETE 像"撤单"；`:id` 是占位符，实际调用时换成某条待办的真实编号。

把草图、字段表、流程和接口表存成 `DESIGN.md`。

## 5. 检查一下

让小白把 `DESIGN.md`（或草图照片）发来。核对：页面三块内容是否齐全？数据字段是否包含 id？四个接口是否对应增删改查？

## 6. 学到了什么

1. 设计 = 画页面、定数据、理流程、列接口，是写代码前的"图纸"。
2. 几乎所有软件对数据的操作都可归纳为 CRUD。
3. 接口是前后端的"合同"，定清楚后两边才能独立开发、顺利对接。

## 7. 记到项目文档

在 `PROJECT_JOURNAL.md` 记录：页面有哪些部分、待办数据有哪些字段、四个接口分别做什么。

## 小白常见问题

- **Q：为什么需要 id，内容不一样不就能区分吗？** A：因为可能出现两条内容相同的待办（比如两条"开会"），id 保证每条都有唯一身份，删除、修改时才不会弄错对象。
- **Q：草图一定要用电脑画吗？** A：不用，纸笔拍照即可，设计的目的是想清楚，而不是画得漂亮。
