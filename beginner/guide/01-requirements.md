# 第 1 步：想清楚做什么——需求与功能清单

> 本步目标：用大白话写清楚"要做一个什么东西、给谁用、有哪些功能"，并学会区分"必须先做的"和"以后再加的"。

## 1. 进度（导师话术）

"这一步一行代码都不写，但它决定了后面所有工作的方向。我们要像开餐厅前先定菜单一样，把要做的功能想清楚。"

## 2. 为什么

- 没想清楚就写代码，容易做了又改、越做越乱，这是新手最常见的坑。
- 把需求写下来，相当于有了一份"合同"，做完后能对照检查"到底做没做成"。

## 3. 概念扫盲

- **需求**：对"软件要能做什么"的描述，越具体越好。
- **功能**：软件能完成的一件具体事情，比如"添加一条待办"。
- **MVP（最小可用版本）**：只包含最核心功能、能真正用起来的第一个版本。就像开店先卖一道招牌菜，跑通了再扩充菜单。
- **用户故事**：一种固定的需求描述句式——"作为【谁】，我希望【做什么】，以便【达到什么目的】"。

## 4. 跟着做

1. 先用两三句大白话回答三个问题：
   - 这个项目是做什么的？
   - 给谁用？
   - 解决他们什么问题？
2. 用"用户故事"句式把功能一条条写出来。以待办清单为例：
   - 作为用户，我希望看到所有待办事项，以便知道还有哪些事要做。
   - 作为用户，我希望添加一条新待办，以便记下要做的事。
   - 作为用户，我希望把一条待办标记为"已完成"，以便看到进度。
   - 作为用户，我希望删除一条待办，以便去掉不要的事项。
3. 给功能分两档：
   - **第一版必须有（MVP）**：上面 4 条增删查改就是核心。
   - **以后再说**：比如设置截止日期、分类、提醒、深色模式、登录账号……先记下来但第一版不做。
4. 把以上内容存成项目里的 `REQUIREMENTS.md`（在 VS Code 里新建文件，写入后保存）。

REQUIREMENTS.md 参考内容：

```markdown
# 我的项目：待办清单

## 项目简介
一个简单的待办清单网站，帮我记录和管理每天要做的事情。

## 目标用户
我自己（以及任何需要记录待办事项的人）。

## 第一版功能（MVP）
1. 查看所有待办事项
2. 添加一条待办
3. 标记一条待办为已完成
4. 删除一条待办

## 以后可能做的功能
- 截止日期和提醒
- 待办分类
- 深色模式
- 用户登录
```

## 5. 检查一下

让小白把写好的 `REQUIREMENTS.md` 内容发给你。核对：是否有项目简介？功能是否用了用户故事或清晰的列表？是否区分了 MVP 和以后功能？

## 6. 学到了什么

1. 动手前先写需求，是所有专业开发的第一步。
2. MVP 思维：先做最小、能用的核心版本，跑通后再迭代，不要一上来追求大而全。
3. 用户故事让需求变得具体、可验证。

## 7. 记到项目文档

在 `PROJECT_JOURNAL.md` 记录：项目要做什么、第一版包含哪些功能、为什么把某些功能放到以后。

## 小白常见问题

- **Q：我想做的功能很多，怎么判断哪些是 MVP？** A：问自己"去掉它，这个产品还能用吗？"——不能用的就是 MVP，锦上添花的都往后放。
- **Q：需求以后能改吗？** A：能，需求变化很正常，但每次改动都更新 REQUIREMENTS.md，做到有据可查。
