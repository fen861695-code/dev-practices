# 代码评审规则（09-review）

## 流程与节奏

- 所有合并到 develop / main 的代码必须经过至少 1 名评审人批准（LGTM），复杂或高风险变更 2 人评审。
- PR 小且聚焦，一次只解决一个问题；过大 PR 应当拆分。
- 评审在提交后 24 小时内响应；作者主动 @ 评审人并附变更说明。
- 合并前所有讨论项必须关闭或明确记录。
- PR 描述必须说明：变更内容、动机、测试情况、影响面、是否破坏性变更。

## 评审原则

- 正确性优先：先确认是否解决问题且无新问题，再讨论风格。
- 设计审查：关注模块边界、复用、扩展性、耦合度。
- 可读性：新成员能否读懂；命名、结构、注释是否自解释。
- 粒度与礼貌：意见说明理由与建议方案，区分"必须修改"与"可选建议"。
- 评审速度：及时评审优于完美评审。

## Reviewer

1. 先看 PR 描述与测试，理解意图，再逐文件阅读。
2. 核对：功能正确性、边界与异常、安全性、性能、可测性、命名与结构。
3. 问题给出明确位置与建议；不理解先提问，不臆断。
4. 原则性问题及时提出；重要问题解决后才批准。
5. LGTM 即代表对变更质量负责。

## 作者

1. 提交前自查：本地测试通过、无调试残留、commit 规范。
2. PR 描述中说明设计决策、备选方案与测试覆盖。
3. 对意见逐一回应；不采纳的说明理由，禁止沉默忽略。
4. 修改后及时回复并重新请求评审。

## 评审检查点

功能一致性与验收标准 / 边界与异常 / 命名结构可读性 / 测试覆盖 / 安全（输入、权限、敏感信息）/ 性能 / 无死代码与未用依赖 / 日志可观测 / 破坏性变更影响评估。
